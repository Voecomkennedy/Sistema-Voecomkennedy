# Atendimento — homologação Supabase local (13/10/2026)

O incremento sintético do branch `codex/atendimento-mvp-sintetico` foi exercitado na pilha **oficial local** do Supabase. Não houve conexão a projeto remoto, alteração de webhook, Z-API, produção ou envio real. O perfil Colima `vck` foi criado no HD externo de UUID `E29E060A-6A14-4E69-AB1F-D7F26F6FB59E`, em `/Volumes/HD externo/Codex-eval-preparation/c`, com 2 CPUs, 4 GiB de RAM, disco de sistema de 8 GiB e disco de dados de 16 GiB. O perfil preexistente `agency-eval` não foi usado. A memória livre do host permaneceu em aproximadamente 31–34%, e o HD externo manteve cerca de 450 GiB livres.

O projeto local está em `/Volumes/HD externo/Codex-eval-preparation/atendimento-supabase-local`. Ele contém somente uma tabela comercial mínima `dados_app` para testes e cópias das duas migrações aditivas de Atendimento. `supabase start` aplicou as duas migrações sem erro. Auth, PostgreSQL, PostgREST, Storage, Kong e Edge Runtime ficaram saudáveis. Os outros serviços foram excluídos da execução. A rede Docker `vck-atendimento-loopback` restringiu a publicação a `127.0.0.1` dentro da VM; um túnel SSH temporário, também em `127.0.0.1`, permitiu testar pelo Mac. Nenhuma porta foi publicada na rede externa.

O teste reproduzível [scripts/atendimento-supabase-integration.mjs](scripts/atendimento-supabase-integration.mjs) exige `VCK_LOCAL_TEST=1`, projeto local com o marcador `.vck-synthetic-only` e URLs de API/banco estritamente locais. Ele usa somente chaves geradas pela CLI para esta stack, mantidas em memória durante a execução. Cria duas contas e eventos sintéticos, testa o handler HTTP com sessão validada pelo GoTrue, RLS de conversas para ambos os proprietários, status anterior à mensagem, deduplicação, descarte de grupo, PDF privado no Storage e negação de leitura para outro usuário e anônimo. Depois exporta backup com bytes e checksum, remove apenas o PDF sintético, esvazia somente as tabelas de Atendimento deste projeto descartável, restaura os bytes e confirma idempotência. O modo `--verify-persistence` confirmou Auth, conversa e PDF íntegros após reiniciar **somente** o contêiner PostgreSQL de teste.

Resultados: integração completa passou; persistência pós-reinício passou; `npm test` passou 123/123; `npm run test:atendimento:db` passou 17/17, incluindo reinício, saída incerta sem reenvio e restauração; `node --check` do novo runner passou. As suites de cotador, Central/Deno e banco da Central já haviam passado antes deste arquivo de teste e não foram repetidas porque o código comercial e da Central não mudou. Não há build/lint/typecheck configurados no `package.json`; a checagem Deno dos módulos já constava da validação anterior.

Limites: a autenticação e o Storage usados foram reais **locais**, mas o transporte permanece sintético, a instância é `mock`, e o handler HTTP foi montado por injeção no teste, sem entrypoint publicado. Isso não valida entrega Z-API, callbacks compartilhados, quotas/latência do Supabase hospedado nem tráfego real. O backup cobre banco e PDF privado; o teste demonstrou restauração com os bytes, não um procedimento de recuperação de desastre do projeto hospedado. A ativação continua desligada por padrão.

Ao terminar, somente este projeto foi parado com `supabase stop --workdir '/Volumes/HD externo/Codex-eval-preparation/atendimento-supabase-local'` **sem** `--no-backup`. O túnel SSH deixou de escutar e `COLIMA_HOME='/Volumes/HD externo/Codex-eval-preparation/c' colima stop --profile vck` confirmou o desligamento. Os discos e volumes locais sintéticos ficaram preservados para auditoria, sem mexer em outros perfis. A memória livre do host voltou a aproximadamente 43%. A próxima etapa é revisar a integração aditiva com o projeto principal e o receptor atual, em autorização separada; não aplicar migrações remotas nem ativar webhooks automaticamente.
